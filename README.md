# Cyber Range IDS & SOC Dashboard

A cybersecurity project designed to simulate security events, detect suspicious network activity, and monitor alerts through a Security Operations Center (SOC) dashboard.

## 📌 Project Overview

The Cyber Range IDS & SOC Dashboard is a security monitoring and attack simulation project developed to demonstrate fundamental concepts of intrusion detection, security alert management, and incident monitoring.

The project combines attack simulation, event analysis, and a web-based dashboard to help users understand how security teams identify and investigate potential cyber threats.

## 🎯 Objectives

- Simulate selected cybersecurity attack scenarios in a controlled lab environment.
- Identify and classify suspicious activities using detection logic.
- Monitor security alerts through a web-based dashboard.
- Store alert information in an SQLite database.
- Understand Red Team, Blue Team, and Purple Team workflows.
- Explore security monitoring and incident response concepts.

## 🛠️ Technologies Used

- **Programming Language:** Python
- **Web Framework:** Flask
- **Frontend:** HTML, CSS, JavaScript
- **Database:** SQLite
- **Intrusion Detection:** Suricata (where configured)
- **Network Analysis:** Wireshark
- **Operating Environment:** Linux / Kali Linux (depending on configuration)

## ⚙️ Key Components

### 1. Red Team — Attack Simulation

The Red Team component represents the offensive security side of the cyber range. It is intended to generate controlled security events for testing detection mechanisms.

Potential scenarios include:

- Denial-of-Service (DoS/DDoS) traffic simulation
- Port scanning
- Web-based attack simulation, such as SQL injection

All testing should be performed only in an authorized, isolated lab environment.

### 2. Blue Team — Detection and Monitoring

The Blue Team component focuses on identifying and monitoring suspicious activity.

The detection engine processes security events and classifies them according to configured rules. Depending on the implemented logic, alerts may include attack categories and severity levels.

### 3. IDS Log Processing

The IDS integration is intended to process security events generated by an intrusion detection system such as Suricata.

Suricata can produce events in EVE JSON format, which can be parsed for further analysis.

The presence of `eve.json` alone does not confirm that live Suricata monitoring is connected to the dashboard.

### 4. SOC Dashboard

The dashboard provides a web interface for viewing security alerts and monitoring the results of detection activities.

The implemented functionality depends on the current application code.

### 5. Database and Alert Storage

SQLite is used to store alert records. The known alert table includes fields such as:

- Alert ID
- Timestamp
- Source IP address
- Attack type
- Severity

The exact schema should be verified against the current database and application code.

### 6. Purple Team — Collaborative Security Testing

The Purple Team concept connects attack simulation with defensive detection. It helps evaluate whether simulated activities are detected and provides a basis for improving security rules.

This describes the project approach; automated Purple Team functionality should only be claimed if implemented.

## 🚀 Getting Started

### Prerequisites

Install the following software as required by your project:

- Python 3
- pip
- Git (optional)
- A supported web browser
- Suricata, if IDS log collection is configured

### 1. Clone the Repository

```bash
git clone <YOUR_REPOSITORY_URL>
cd cyber-range-ids-soc-dashboard
```

Replace `<YOUR_REPOSITORY_URL>` with your actual repository URL. If the project is already on your computer, navigate directly to its directory.

### 2. Create a Virtual Environment

```bash
python -m venv venv
```

Activate it on Linux or Kali Linux:

```bash
source venv/bin/activate
```

On Windows:

```powershell
.\venv\Scripts\Activate.ps1
```

### 3. Install Dependencies

If `requirements.txt` exists and contains the required packages, run:

```bash
pip install -r requirements.txt
```

If the file is missing or incomplete, install dependencies according to the actual Python imports in the project.

### 4. Run the Application

Navigate to the dashboard directory:

```bash
cd dashboard
```

Run the Flask application:

```bash
python app.py
```

Open the local address shown in the terminal. If the application uses Flask's default port, it is usually:

```text
http://127.0.0.1:5000
```

Use the port configured in `app.py` if it differs from the default.

## 📊 Alert Classification

The detection logic may classify events into categories such as:

| Alert Category | Description |
|---|---|
| DDoS / Flood | Traffic patterns classified as flooding activity |
| Port Scan | Activity associated with scanning network ports |
| Brute Force | Repeated authentication attempts, if detected |
| Web Attack | Suspicious web activity, if detected |
| Unknown | Events that do not match configured categories |

Severity levels such as High, Medium, and Low depend on the implemented classification rules.

**Important:** These classifications are based on detection logic and do not independently prove that an actual attack occurred. Verify each category against the current implementation.

## 🔐 Security Considerations

- Perform simulations only on systems and networks you own or have explicit permission to test.
- Do not expose the development dashboard to public networks without appropriate security controls.
- Avoid committing passwords, API keys, tokens, or other secrets.
- Validate and sanitize untrusted input.
- Use parameterized SQL queries where database input is involved.
- Restrict access to sensitive security logs.
- Treat detection results as indicators requiring investigation, not definitive proof of malicious activity.

## ⚠️ Limitations

- Detection accuracy depends on the configured rules and available event data.
- Simulated attacks do not fully reproduce real-world attack conditions.
- Dashboard functionality depends on the features implemented in the current codebase.
- Live traffic monitoring and automated prevention should not be assumed unless verified.
- Further testing is required to assess detection accuracy, reliability, and performance.
